# Личная CRM

Контакты людей, которых я знаю лично. Идея и ограничения — в `specs/01-продуктовая-идея.md`.

Что умеет:

- вход по ссылке из письма, без пароля: на странице входа вводишь почту, получаешь письмо с кнопкой «Войти» и попадаешь в приложение. Ссылка работает один раз и 15 минут, вход на устройстве держится 30 дней с последнего захода. Первый вход под новой почтой и есть регистрация. В шапке — почта и «Выйти» (выходит только на этом устройстве). На почту — не больше 3 писем за 10 минут, с одного адреса в интернете — не больше 10 за час;
- у каждого пользователя свои контакты, заметки и группы: чужое не видно ни в списке, ни в поиске, ни по прямой ссылке (там «Контакт не найден»). Новый пользователь начинает с пустого списка и без групп;
- список контактов по алфавиту, по 50 на странице (можно выбрать 10, 20 или 50 — справа над списком), внизу — переключатель страниц;
- поиск по имени по всем контактам (без учёта регистра, «е» и «ё» — одно и то же); найденное тоже разбито на страницы;
- добавить контакт: имя, кто это, откуда знакомы, телефон, почта и как часто общаться (раз в неделю, месяц, квартал, год или «не задано»);
- карточка контакта: исправить данные, дописать заметку после разговора (заметки идут с датой, новые сверху).
- удалить контакт из карточки или из списка — вместе с заметками; 10 секунд можно нажать «Отменить» и вернуть всё как было.
- блок «Пора связаться» над списком: люди, с которыми не общался дольше заданной частоты, самые просроченные сверху (сначала 5, остальные — по «Показать всех»). Общение — это заметка или кнопка «Связался» в строке блока: она убирает человека из блока, не создавая заметку. Пока идёт поиск, блока нет.
- группы: страница «Группы» (кнопка «Группы» на главной рядом с заголовком) — пять готовых групп («Аналитики», «Друзья», «Знакомые», «Семья», «Теннис») и свои; у каждой видно, сколько в ней людей. Группу можно создать, переименовать и удалить; название — до 50 символов, «Семья» и «семья» (как и «Ёлки» и «Елки») считаются одним названием. При удалении сначала спрашивают, потом 10 секунд можно нажать «Отменить» — группа вернётся с теми же людьми; сами люди при удалении группы остаются в контактах.
- группы у человека: в форме «Добавить контакт» и «Изменить» есть поле «Группы» — нажмите нужные (можно несколько или ни одной); в карточке контакта строка «Группы» и кнопка «Изменить группы»: открывается список с флажками, каждая отметка сохраняется сразу, без кнопки «Сохранить». Если удалить контакт и нажать «Отменить», он вернётся в те же группы.
- фильтр по группам над списком: «Все», каждая группа и «Без группы». Если выбрать несколько групп, останутся люди, которые есть во всех них сразу. Фильтр работает вместе с поиском и счётчиком («Найдено: 3 из 120»), хранится в адресе страницы (обновили страницу или открыли ссылку — фильтр тот же) и действует и на общий список, и на блок «Пора связаться»: в нём остаются только подходящие люди. В строке каждого человека видны метки его групп: нажатие на метку добавляет эту группу к фильтру, а метка в карточке открывает главную только с этой группой.

Данные лежат в базе на этом компьютере, поэтому в любом браузере, где вы вошли под своей почтой, видны одни и те же контакты.
Локальная версия открывается только на этом компьютере (`127.0.0.1`), другим устройствам в сети она не видна. Письма со ссылкой для входа здесь никуда не уходят: их ловит почтовая заглушка Mailpit, письма читаются на странице <http://127.0.0.1:8025>.

Версия на сервере — <https://app.percrm.ru>, со своей базой. Войти можно по ссылке из письма: на сервере письма настоящие (через Resend). Как она обновляется — в разделе «Выкатка на сервер».

## Что нужно

- Docker Desktop (должен быть запущен)
- Node.js 24 и pnpm
- OpenSpec — для работы над фичами с агентом (см. «Как делаем фичи»)

## Первый запуск на новом компьютере

1. Скопировать `.env.example` в `.env` и заполнить значения (пароль — любой длинный случайный). Для входа нужны ещё шесть строк:

   ```
   OWNER_EMAIL=ваша почта: все данные, что были до входа, достанутся этому пользователю
   BETTER_AUTH_SECRET=вывод команды: openssl rand -base64 32
   BETTER_AUTH_URL=http://127.0.0.1:3000
   SMTP_URL=smtp://127.0.0.1:1025
   MAIL_FROM="Личная CRM <ваша почта>"
   MAILPIT_URL=http://127.0.0.1:8025
   ```
2. Установить зависимости:

   ```sh
   pnpm install
   ```

3. Запустить базу и почтовую заглушку Mailpit:

   ```sh
   docker compose up -d --wait
   ```

4. Создать таблицы в базе (команда берёт `OWNER_EMAIL` из `.env`: если в базе уже есть контакты или группы, они станут данными этого пользователя; без `OWNER_EMAIL` миграция остановится и ничего не изменит):

   ```sh
   pnpm db:migrate
   ```

5. По желанию — наполнить базу тестовыми данными (1000 контактов с заметками у пользователя `OWNER_EMAIL`; примерно две трети людей лежат в одной-двух из его групп «Аналитики», «Друзья», «Знакомые», «Семья», «Теннис», если они есть, остальные без групп). Если у владельца уже есть контакты, ничего не добавляется, данные других пользователей не трогаются:

   ```sh
   pnpm db:seed
   ```

6. Запустить приложение и открыть <http://127.0.0.1:3000> (именно этот адрес, как в `BETTER_AUTH_URL`):

   ```sh
   pnpm dev
   ```

## Каждый день

1. Запустить Docker Desktop — база стартует вместе с ним. Если её останавливали командой `docker compose down`, запустить снова: `docker compose up -d --wait`.
2. `pnpm dev` и открыть <http://127.0.0.1:3000>.
3. Остановить приложение — `Ctrl + C` в терминале.

## Как проверить, что всё работает

0. Открыть <http://127.0.0.1:3000> — откроется страница входа. Ввести свою почту → «Получить ссылку» → под формой «Ссылка для входа отправлена на …». Открыть <http://127.0.0.1:8025>, нажать «Войти» в письме — вы в приложении, в шапке ваша почта и «Выйти». Ввести неверный адрес (`anna@`) — «Проверьте адрес почты», письма нет. Четыре запроса подряд на одну почту — на четвёртом «Слишком часто…». В окне инкогнито войти под другой почтой — список пуст («Здесь пока никого нет» и кнопка «Добавить контакт»), контактов первого пользователя не видно, а его адрес карточки показывает «Контакт не найден».
1. Открыть <http://127.0.0.1:3000> — видны первые 50 контактов, их общее количество и переключатель страниц внизу. «Дальше» открывает следующие 50. «Показывать по 10» справа над списком — на странице 10 контактов, страниц становится больше.
2. «Добавить контакт» → заполнить имя → «Добавить». Откроется страница списка, где оказался новый контакт: список прокрутится к нему и подсветит его.
3. Ввести часть имени в поиск → открыть карточку → написать заметку → «Добавить заметку».
4. Обновить страницу — заметка на месте.
5. Открыть тот же адрес в другом браузере (например, Safari) — те же контакты и та же заметка.

   Шаги 1–5 (кроме переключателя страниц) проверяет и `pnpm test:e2e` — см. «e2e-тесты».
6. В карточке контакта нажать «Удалить» — откроется тот же список, где вы были, контакта в нём нет. Внизу 10 секунд висит «Контакт удалён» с кнопкой «Отменить»: она возвращает контакт со всеми заметками и снова открывает карточку.
7. В списке навести мышь на строку — справа появится корзина. Нажать — строка сразу пропадёт, «Отменить» вернёт её на место. На телефоне корзина видна всегда.
8. Открыть контакт с давней заметкой (больше месяца назад) → «Изменить» → «Как часто общаться: Раз в месяц» → «Сохранить». На главной над поиском появится блок «Пора связаться» с этим человеком.
9. Нажать у него «Связался» — он сразу пропадёт из блока, внизу появится «Отмечено: <имя>». В его карточке заметок столько же, сколько было.
10. Задать «Раз в месяц» другому контакту с давней заметкой — он в блоке. Открыть его из блока, написать заметку, вернуться на главную — в блоке его больше нет.
11. Нажать «Группы» на главной — видны пять готовых групп с числом людей. «Создать группу» → «Работа» → «Сохранить»: группа встала в список по алфавиту. «Удалить» у «Работа» → «Удалить»: внизу 10 секунд висит «Группа «Работа» удалена» с кнопкой «Отменить».
12. Положить двух людей в «Друзья», одного из них ещё в «Теннис» (в карточке: «Изменить группы» → поставить флажки). На главной выбрать «Друзья» и «Теннис» — виден один. Обновить страницу — фильтр тот же. Нажать «Без группы» — этих двоих в списке нет.

| Что сделать | Команда |

| Письма, которые отправило приложение | <http://127.0.0.1:8025> (Mailpit) |
| После изменения схемы в `src/db/schema.ts` — подготовить миграцию | `pnpm db:generate` |
| Проверить код | `pnpm lint` |
| Проверить типы | `pnpm typecheck` |
| Проверить, что код оформлен по правилам | `pnpm format:check` |
| Оформить код по правилам (переносы строк, пробелы) | `pnpm format` |
| Запустить автотесты | `pnpm test` |
| Запустить e2e-тесты (сценарии в браузере) | `pnpm test:e2e` |

Для `pnpm test` нужны запущенные база и Mailpit (`docker compose up -d --wait`): тесты отправляют настоящие письма, но в Mailpit, и читают их оттуда. Тесты идут в отдельной базе `<имя вашей базы>_test` в том же контейнере: `pnpm test` сам создаёт её и применяет миграции, а рабочая база и её контакты не трогаются. Если база не запущена, `pnpm test` сразу пишет, что подключиться не удалось, и подсказывает команду запуска. Строку «No test files found» ниже можно не читать: её добавляет сам Vitest.

### e2e-тесты

`pnpm test:e2e` проходит главный сценарий так же, как человек: входит под пользователем (форма входа, письмо в Mailpit, ссылка из него), в настоящем браузере открывает список, добавляет контакт, находит его по имени, дописывает заметку, обновляет страницу и открывает тот же адрес во втором, чистом браузере. Тест сам собирает «боевую» версию приложения, запускает её так же, как Docker-образ на сервере, на <http://127.0.0.1:3100> и со своей базой `<имя вашей базы>_e2e`: рабочие контакты и запущенный `pnpm dev` он не трогает. Один прогон — около 20 секунд, большая часть — сборка.

- Нужны запущенные база и Mailpit, как для `pnpm test`. Отдельный файл `e2e/login.spec.ts` проверяет вход, шапку, пустой список и главное требование: пользователь B не видит контакты пользователя A ни в списке, ни в поиске, ни по прямой ссылке.
- На новом компьютере один раз скачать браузер для тестов: `pnpm exec playwright install chromium`.
- Если тест упал, в выводе видно, на каком шаге. Посмотреть, как выглядела страница на каждом шаге, — команда `pnpm exec playwright show-trace ...` из вывода.

## База данных

PostgreSQL работает локально в Docker. Настройки подключения лежат в `.env`, его нет в git.
Приложение берёт из `.env` те же `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` и `POSTGRES_PORT`, что и Docker.
Если в `.env` задан `DATABASE_URL`, используется он.

Полезные команды:

| Что сделать | Команда |
|---|---|
| Запустить базу | `docker compose up -d --wait` |
| Посмотреть, работает ли | `docker compose ps` (статус `healthy` — всё хорошо) |
| Зайти в базу консолью | `docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'` |
| Остановить базу (данные сохранятся) | `docker compose down` |

Данные хранятся в Docker-томе `personal-crm_db-data` и переживают остановку и перезапуск.
Команда `docker compose down -v` **удалит все данные** базы.

## Как делаем фичи

Фичи проектируем с агентом через [OpenSpec](https://openspec.dev): сначала требования и план, потом код. Документы пишутся по-русски.

Установить OpenSpec на новом компьютере (один файл, ставится в `~/.local/bin`):

```sh
curl -fsSL https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/scripts/binary/install.sh | sh
```

Команды в Claude Code:

| Что сделать | Команда |
|---|---|
| Обдумать идею, ничего не меняя | `/opsx:explore` |
| Описать фичу: требования, план, задачи | `/opsx:propose <что хотим>` |
| Сделать фичу по плану | `/opsx:apply` |
| Поправить требования или план | `/opsx:update` |
| Закрыть сделанную фичу (требования переедут в `openspec/specs/`) | `/opsx:archive` |
| Пересказать фичу простыми словами | `/feature-overview` |

Обновить OpenSpec: `openspec install`, затем в папке проекта `openspec update`.

## Проверки pull request (CI)

На каждый pull request GitHub Actions запускает проверки (`.github/workflows/ci.yml`):

| Проверка | Что проверяет | Повторить у себя |
|---|---|---|
| Lint | ошибки в коде | `pnpm lint` |
| Format | код оформлен по правилам Prettier | `pnpm format:check`, исправить — `pnpm format` |
| Types | типы TypeScript сходятся | `pnpm typecheck` |
| Unit tests | автотесты Vitest на настоящей базе Postgres и настоящем Mailpit | `pnpm test` |
| E2E tests | вход и главный сценарий в настоящем браузере | `pnpm test:e2e` |
| Build image | Docker-образ для сервера собирается | — |

Базу и Mailpit для тестов CI поднимает сам, только на время проверки; ключ входа `BETTER_AUTH_SECRET` создаётся заново на каждый запуск и нигде не хранится. Сервер и рабочие контакты проверки не трогают.

Результат — внизу страницы pull request. Зелёные галочки — всё прошло. Красный крестик — ссылка **Details** ведёт в лог, там видно, что упало. Если упал e2e-тест, на странице запуска внизу есть архив `playwright-traces`: скачать, распаковать и открыть `pnpm exec playwright show-trace <файл trace.zip>`.

Правила ветки `main` на GitHub (Settings → Branches):

- в `main` попадает только pull request: push напрямую в `main` не пройдёт, даже от владельца;
- pull request вливается, только когда все шесть проверок зелёные и ветка не отстала от `main`. Отстала — кнопка **Update branch** на странице pull request, проверки пройдут заново;
- автовлитие: агент сразу после открытия pull request включает «влить, когда проверки пройдут» (`gh pr merge --auto --squash`). Pull request вольётся сам и сразу выкатится на сервер. Передумали — кнопка **Disable auto-merge** на странице pull request.

## Выкатка на сервер

Каждый merge pull request в `main` сам выкатывает новую версию:

1. GitHub Actions собирает Docker-образ, тег — SHA коммита, и кладёт его в GHCR: `ghcr.io/vdanil61/personal-crm`.
2. Копирует на сервер всю папку `deploy/` (новый скрипт в ней уезжает сам) и запускает `deploy.sh`:
   - бэкап базы — копия в папке `backups/` на сервере (см. «Бэкапы и восстановление»). Если бэкап не снялся — дальше выкатка не идёт, работает старая версия;
   - разовый контейнер из нового образа применяет миграции базы и завершается. Если миграции упали — новая версия не стартует, работает старая;
   - запускает новую версию приложения;
   - smoke-проверка: `/health` должен ответить 200;
   - удаляет старые образы, оставляет текущий и предыдущий; из бэкапов оставляет 10 последних.

Для выкатки в `.env` на сервере должны быть строки `OWNER_EMAIL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `SMTP_URL` и `MAIL_FROM` (см. «Сервер»). Любой из них не хватает — `docker compose` останавливает выкатку на первой же команде, до бэкапа и миграций, и работает прежняя версия.

Pull request на сервер не попадает: его только проверяет CI (см. «Проверки pull request»).

Ход выкатки — в репозитории на GitHub: вкладка **Actions** → **Deploy**. Зелёная галочка — новая версия работает, красный крестик — выкатка упала: в логе видно, на каком шаге.

Проверить руками: открыть <https://app.percrm.ru/health> — должно быть `{"status":"ok"}`.

### Если выкатка упала

Автоматического отката нет. Откатиться на предыдущую версию — вручную, командой на своём компьютере:

```sh
ssh -t crm sudo -u deploy /home/deploy/personal-crm/rollback.sh
```

Откат возвращает только код: изменения базы (миграции) остаются. Перед откатом, как перед любой выкаткой, снимается бэкап базы. Вернуть саму базу — см. «Бэкапы и восстановление».

**После выкатки входа откат — только вместе.** Миграции входа добавили владельца всем контактам и группам, и прежняя версия приложения с такой базой не работает. Поэтому: сначала `rollback.sh` (прошлая версия приложения), затем `restore.sh` с копией, снятой перед выкаткой входа (файл с версией, которая стояла до неё). Всё, что добавили в приложении после выкатки входа, при таком откате пропадёт. Запускает владелец.

### Бэкапы и восстановление

Перед каждой выкаткой (и перед откатом) снимается бэкап базы прода — файл в `/home/deploy/personal-crm/backups` на сервере. Имя файла — когда снят и на какой версии приложения:

```
2026-11-03_184005_bb81497.dump
```

- `2026-11-03_184005` — дата и время по UTC (по Москве на 3 часа больше): 18:40:05;
- `bb81497` — версия приложения, которая стояла **до** выкатки: первые 7 знаков коммита, как их показывает GitHub. В бэкапе таблицы именно этой версии — миграции новой версии идут уже после него.

Хранятся 10 последних файлов, старые удаляются после удачной выкатки. Бэкапы лежат на том же сервере: от испорченной миграции или удалённых данных они спасут, от потери самого сервера — нет.

Посмотреть список бэкапов:

```sh
ssh -t crm sudo -u deploy /home/deploy/personal-crm/restore.sh
```

Восстановить базу из бэкапа — только вручную, этой командой (агент её не запускает):

```sh
ssh -t crm sudo -u deploy /home/deploy/personal-crm/restore.sh <имя файла из списка>
```

1. Скрипт показывает, какой файл загрузит и какую базу заменит, и ждёт, пока вы наберёте `yes`. Любой другой ответ — ничего не меняется.
2. Если бэкап снят на другой версии приложения, чем стоит сейчас, скрипт пишет `WARNING`: таблицы могут отличаться, и приложение после восстановления может не подняться. Обычно сначала откатывают приложение на версию бэкапа (`rollback.sh`, если это предыдущая версия — её видно в конце лога выкатки), потом восстанавливают.
3. После `yes`:
   - снимает копию текущей базы — файл `..._before-restore.dump` в той же папке;
   - останавливает приложение;
   - удаляет базу, создаёт её заново пустой и загружает бэкап;
   - запускает приложение той же версии, что было, и проверяет `/health`.

Restore не меняет версию приложения и не запускает миграции. Пока он идёт, сайт не открывается, а выкатка из GitHub ждать не будет — упадёт с «Another deploy or restore is running»: её можно перезапустить (Actions → Deploy → **Re-run jobs**).

Если restore упал, в конце написано, на каком шаге, и готовая команда, чтобы вернуть базу, какой она была до restore (из файла `..._before-restore.dump`).

### Тестовые данные на сервере

GitHub → **Actions** → **Seed test data** → **Run workflow**. Демо-данные создаются у пользователя `OWNER_EMAIL`; если у него уже есть контакты, ничего не добавляется (в логе «demo data skipped»). Данные других пользователей не трогаются.

### Сервер

- Приложение работает от пользователя `deploy` в папке `/home/deploy/personal-crm`: там `compose.yaml` (проект `prod`), скрипты, `.env` с паролем базы и настройками входа (права 600, в git нет — образец в `deploy/.env.example`), история выкаток `releases.log`, бэкапы базы в `backups/` (папка и файлы читает только `deploy`).
- nginx отправляет `app.percrm.ru` в приложение (`deploy/nginx/app.percrm.ru.conf`) и передаёт ему настоящий адрес посетителя в `X-Real-IP`: по нему считается лимит писем.
- Письма входа на сервере идут через [Resend](https://resend.com) по SMTP. Отправитель — `noreply@mail.percrm.ru`: Resend отправляет только с домена, который подтверждён записями DNS, поэтому для писем заведён поддомен `mail.percrm.ru` (записи percrm.ru для лендинга и приложения не менялись). Строки в `.env` на сервере:

  ```
  OWNER_EMAIL=почта владельца
  BETTER_AUTH_SECRET=новый ключ (openssl rand -base64 32), не тот, что на компьютере
  BETTER_AUTH_URL=https://app.percrm.ru
  SMTP_URL=smtps://resend:<ключ Resend>@smtp.resend.com:465
  MAIL_FROM="Личная CRM <noreply@mail.percrm.ru>"
  ```
- Сервер подготовлен один раз скриптом `deploy/setup-server.sh` (пользователь `deploy`, ключ для GitHub, nginx).
- В настройках репозитория на GitHub: секрет `DEPLOY_SSH_KEY` (ключ, которым Actions заходит на сервер), переменные `DEPLOY_HOST` и `DEPLOY_KNOWN_HOSTS` (адрес сервера и его отпечаток).
