# Design

## Context

Зачем фича — см. `proposal.md`, «Why». Что должно работать — `specs/user-auth`, `specs/data-ownership`, `specs/contact-groups`.

Как сейчас:

- Входа нет. Любой, кто открыл app.percrm.ru, видит все данные.
- Таблицы: `contacts`, `notes`, `groups`, `contact_groups`. Ни у одной нет владельца.
- Уникальность названия группы держит индекс `groups_name_unique_idx` по `replace(lower(name), 'ё', 'е')` — на всю базу.
- Миграция `0003_default_groups.sql` вставляет пять готовых групп в любую базу, даже новую.
- Весь доступ к базе — в `src/lib/contacts.ts`, `src/lib/groups.ts` и серверных действиях `src/app/actions.ts` (серверное действие — функция, которую форма в браузере вызывает на сервере). Страницы — серверные компоненты в `src/app/`.
- Подключение к базе ленивое (`getDb()`): `next build` в Docker собирается без настроек базы. Всё новое, что читает настройки, должно быть таким же ленивым.
- Миграции на сервере применяет `scripts/migrate.ts` в разовом контейнере. До него `deploy.sh` снимает бэкап. Локально `pnpm db:migrate` пока вызывает `drizzle-kit migrate`.
- Тесты:
  - Vitest — на настоящей базе `<имя>_test`. `cleanDb` очищает все таблицы и снова вставляет готовые группы текстом миграции 0003. Подменяется только `next/cache`.
  - Playwright — на базе `<имя>_e2e`, против собранного приложения на порту 3100. Код приложения он импортировать не может: `server-only` в `src/db/index.ts`.
- В CI шесть обязательных задач с неизменными именами, это и есть защита main.
- nginx уже передаёт приложению заголовок `X-Real-IP` с настоящим адресом посетителя.
- Агент не имеет доступа к Docker на сервере. `.env` на сервере и локально пишет только владелец.
- Репозиторий публичный: всё в git, логи GitHub Actions и выводы скриптов выкатки видны всем. Почты и ключи туда не попадают.

## Goals / Non-Goals

**Goals:**

- Ни одного пути к чужим данным: ни через страницу, ни через серверное действие, ни через ссылку. Сервер узнаёт пользователя сам, данным из браузера о владельце не верит.
- Миграция существующих данных — всё или ничего. Без почты владельца она останавливается, ничего не меняя.
- Одна сборка образа для компьютера, CI и сервера. Различаются только настройки.
- Тесты по-прежнему на настоящей базе и с настоящими письмами, в Mailpit.

**Non-Goals:**

- Защита на уровне самой базы (Row-Level Security — правила доступа к строкам внутри Postgres). Она надёжнее, но сложна с общим пулом соединений; сейчас фильтр по владельцу стоит в коде и проверяется тестами.
- Чистка старых входов и записей о письмах по расписанию. Записи о письмах чистятся по ходу дела, устаревшие входы лежат и не мешают.
- Перенос данных между пользователями.

## Decisions

### 1. Better Auth: ленивый экземпляр и его настройки

`src/lib/auth/auth.ts` создаёт экземпляр Better Auth при первом обращении (`getAuth()`), как `getDb()`. Так `next build` не требует настроек входа. Обработчик Better Auth стоит на `src/app/api/auth/[...all]/route.ts`. Настройки:

- База — через адаптер Drizzle. Таблицы во множественном числе, как наши (`users`, `sessions`, `accounts`, `verifications`). Идентификаторы — `uuid`, как у `contacts` и `groups`: тогда номер пользователя проверяется той же схемой, что и номер контакта.
- Плагин magic link:
  - `expiresIn: 900` (15 минут).
  - `storeToken: "hashed"`: в базе лежит отпечаток ссылки, а не она сама.
  - `sendMagicLink` отправляет письмо (решение 5).
  - Регистрация при первом входе не выключена. Ссылка одноразовая сама: Better Auth тратит её при первом открытии.
- Куда ведёт ссылка: удачный вход и первый вход — на `/`, любая ошибка — на `/login/expired`.
- Вход (session — запись о входе на одном устройстве): `expiresIn` — 30 дней, `updateAge` — 1 час. Срок сдвигается при заходе, если с прошлого сдвига прошло больше часа. Кэш входа в куки (`cookieCache`) выключен: выход и истёкший вход видны сразу.
- Встроенный лимит запросов Better Auth выключен. Он хранится в памяти, сбрасывается при перезапуске и в e2e не дал бы входить чаще 5 раз в минуту с одного адреса. Свои лимиты — решение 4. Подобрать ссылку перебором нельзя: она длинная и случайная.
- Плагин `nextCookies()`: серверные действия могут ставить и стирать куки входа.
- Пароли выключены (в Better Auth они включаются отдельно, мы их не включаем).

Отвергнуто: свой код ссылок и входов. Better Auth задан спекой, а самописный вход — частый источник дыр.

Точные имена настроек сверяю с документацией установленной версии при реализации. Схема таблиц Better Auth — по его документации, с нашими именами таблиц.

### 2. Таблицы

Новые таблицы Better Auth (поля — как требует Better Auth):

- `users`: `id`, `name`, `email` (уникальная, всегда маленькими буквами), `email_verified`, `image`, `created_at`, `updated_at`.
- `sessions`: `user_id`, `token`, `expires_at`, … Удалился пользователь — его входы удаляются вместе с ним.
- `accounts`: нужна Better Auth, вход по ссылке её почти не использует.
- `verifications`: ссылки для входа — отпечаток, почта, срок.

Своя таблица `login_link_requests` — по ней считаются лимиты:

- поля: `id`, `email`, `ip`, `created_at`;
- индексы по (`email`, `created_at`) и (`ip`, `created_at`).

Изменения в наших таблицах:

- `contacts.user_id` и `groups.user_id` — `uuid not null`, ссылки на `users.id` без каскада. Пользователя с данными база удалить не даст.
- Индекс `contacts_user_id_idx`.
- `groups_name_unique_idx` заменяется на `groups_user_id_name_unique_idx` по (`user_id`, `replace(lower(name), 'ё', 'е')`). Одинаковые названия у разных пользователей разрешены, у одного — нет.
- `notes` и `contact_groups` не меняются. Владелец заметки и связи — владелец контакта.

Отвергнуто: `user_id` у `notes` и `contact_groups`. Это дублирование, которое может разойтись с контактом. Владелец определяется через контакт и группу, а код проверяет, что контакт и группа в связи принадлежат одному пользователю (решение 7).

### 3. Три миграции и почта владельца

- **`0004_login`** (создаёт `drizzle-kit generate`):
  - создаёт таблицы входа и `login_link_requests`;
  - добавляет `contacts.user_id` и `groups.user_id` пока необязательными, без ссылок.
  - Существующие данные не меняются.
- **`0005_owner_data`** (пишется вручную: `drizzle-kit generate --custom`). Это единственная миграция, которая меняет существующие данные; её владелец смотрит до merge. Что она делает:
  - Если в `contacts`, `notes` или `groups` нет ни одной строки — ничего.
  - Иначе читает почту владельца из настройки соединения `app.owner_email`, убирает пробелы по краям и делает буквы маленькими. Пусто — останавливается с ошибкой «OWNER_EMAIL is not set: existing contacts and groups need an owner». Саму почту в сообщения она не пишет: логи выкатки публичные.
  - Создаёт пользователя с этой почтой (`email_verified = true`), если его нет.
  - Ставит его `user_id` всем контактам и группам.
  - Заметки, связи с группами, частоты и отметки «Связался» не трогает: они уже принадлежат контактам.
- **`0006_owner_required`** (создаёт `drizzle-kit generate`):
  - делает `user_id` обязательным и добавляет ссылки на `users`;
  - создаёт `contacts_user_id_idx`;
  - заменяет индекс названий групп.
  - Если где-то остался `user_id = null`, миграция падает: данные без владельца пройти не могут.

Все ожидающие миграции Drizzle применяет одной транзакцией (всё или ничего). Если 0005 или 0006 упала, база остаётся на 0003, а прежняя версия приложения работает. Это проверяет тест миграции (решение 10).

Новая база (компьютер нового разработчика, тестовые базы) тоже получает пять готовых групп из 0003. Значит, в ней уже есть данные, и миграциям нужна почта владельца. Группы достаются владельцу.

Как почта попадает в миграцию:

- Общая функция `applyMigrations(url, ownerEmail)` (новый `src/db/apply-migrations.ts`, без `server-only`) открывает пул из одного соединения.
- Выполняет `select set_config('app.owner_email', $1, false)`: почта передаётся параметром, не вклеивается в текст SQL.
- На том же соединении запускает миграции Drizzle.
- Её вызывают:
  - `scripts/migrate.ts` с `OWNER_EMAIL` из окружения — и на сервере, и локально: `pnpm db:migrate` теперь `tsx scripts/migrate.ts`;
  - подготовка тестовых баз — с тестовой почтой владельца.

Отвергнуто:

- почта в тексте миграции — репозиторий публичный;
- отдельный скрипт после миграций — не атомарно: приложение могло бы стартовать с данными без владельца;
- «данные получает первый вошедший» — владелец отказался.

### 4. Запрос ссылки, проверка почты и лимиты

Форма на `/login` вызывает серверное действие `requestLoginLink`:

- Берёт почту из формы.
- Проверяет общей схемой `loginEmailSchema` (`src/lib/validation.ts`): убрать пробелы по краям, сделать буквы маленькими, проверить адрес, не длиннее 254 знаков. Ошибка — «Проверьте адрес почты».
- Вызывает `auth.api.signInMagicLink` с заголовками запроса.
- Переводит ответ в текст: отправлено, неверная почта, «Слишком часто…», «Не удалось отправить письмо…».

Чтобы те же правила действовали и на запрос в обход формы (прямой POST на `/api/auth/sign-in/magic-link`), проверки стоят в перехватчике Better Auth: `hooks.before` для пути `/sign-in/magic-link`. Он срабатывает при любом вызове этого пути. Перехватчик:

1. Нормализует и проверяет почту той же `loginEmailSchema`. Неверная — отказ «неверная почта».
2. Берёт адрес посетителя: `X-Real-IP` (его ставит nginx и перезаписывает присланный снаружи), иначе первый адрес из `X-Forwarded-For`, иначе `unknown`.
3. В одной транзакции под общей блокировкой (`pg_advisory_xact_lock`): так два одновременных запроса не проскочат лимит.
   - Считает записи `login_link_requests` по этой почте за 10 минут (лимит 3) и по этому адресу за 60 минут (лимит 10). Превышен любой — отказ «слишком часто», запись не добавляется.
   - Иначе добавляет запись и удаляет записи старше суток.
   - Удаляет из `verifications` прежние ссылки на эту почту: «новая ссылка отменяет старые».
4. Пропускает запрос дальше. Better Auth создаёт новую ссылку и вызывает `sendMagicLink`.

Запись добавляется до отправки. Неудачная отправка тоже тратит лимит: это проще и не даёт долбить сломанную почту.

Отвергнуто: проверки только в серверном действии. Тогда прямой запрос к Better Auth обходил бы их. Это прямо запрещено спекой.

### 5. Письма: Nodemailer и настройки

`src/lib/mail.ts` лениво создаёт транспорт Nodemailer из `SMTP_URL` (SMTP — протокол отправки почты; транспорт — объект, через который Nodemailer шлёт письма). Письмо входа собирает `src/lib/auth/login-email.ts`:

- отправитель — `MAIL_FROM`;
- тема «Вход в Личную CRM»;
- письмо в двух видах: оформленное (HTML) с кнопкой «Войти» и простой текст со ссылкой;
- строки про 15 минут и «Если вы не запрашивали вход — просто проигнорируйте письмо».

Оформление письма — простые встроенные стили в цветах приложения: почтовые программы не понимают наши дизайн-токены.

Настройки (все в `.env`, образец без значений — в `.env.example` и `deploy/.env.example`):

| Настройка | На компьютере | В CI | На сервере |
|---|---|---|---|
| `OWNER_EMAIL` | почта владельца | не нужна: тесты передают свою | почта владельца |
| `BETTER_AUTH_SECRET` | случайная строка | создаётся на каждый запуск | случайная строка |
| `BETTER_AUTH_URL` | `http://127.0.0.1:3000` | e2e: `http://127.0.0.1:3100` (ставит `playwright.config.ts`) | `https://app.percrm.ru` |
| `SMTP_URL` | `smtp://127.0.0.1:1025` (Mailpit) | `smtp://127.0.0.1:1025` | `smtps://resend:<ключ Resend>@smtp.resend.com:465` |
| `MAIL_FROM` | `Личная CRM <v.danil903@gmail.com>` | тестовый адрес, например `Личная CRM <noreply@example.com>`: файл CI публичный, почты владельца в нём нет | `Личная CRM <noreply@mail.percrm.ru>` |
| `MAILPIT_URL` | `http://127.0.0.1:8025`, только тестам | то же | не нужна |

Resend принимает письма по SMTP. Поэтому и Mailpit, и Resend — один и тот же код Nodemailer, разница только в `SMTP_URL`.

Resend отправляет только с адреса на домене, подтверждённом в нём записями DNS. gmail.com подтвердить нельзя, поэтому на сервере отправитель — `noreply@mail.percrm.ru`. Поддомен `mail.percrm.ru` нужен только для писем: записи percrm.ru для лендинга и приложения не меняются. Mailpit принимает письмо с любого адреса, поэтому на компьютере владельца отправитель — его Gmail. Нет нужной настройки — приложение падает с понятной ошибкой при первой отправке или при первом входе, а не молча.

Mailpit локально — новый сервис в `compose.yaml` (образ `axllent/mailpit`, последняя стабильная версия, сейчас v1.33.0 — перепроверю при установке):

- SMTP на `127.0.0.1:1025`;
- страница на `127.0.0.1:8025`;
- только для этого компьютера, без хранения писем между перезапусками.

### 6. Кто сейчас вошёл: proxy и проверки на сервере

- `src/lib/auth/session.ts`:
  - `getCurrentUser()` — один запрос `auth.api.getSession` на запрос страницы (через `cache` из React);
  - `requireUser()` — то же, но без входа отправляет на `/login`.
  - Каждая страница с данными и каждое серверное действие начинают с `requireUser()` и дальше работают только с `user.id`.
- `src/proxy.ts` (в Next.js 16 так называется код, который срабатывает перед страницей):
  - для обычного открытия страниц, кроме `/login`, `/login/expired`, `/api/auth/…`, `/health` и файлов `_next`, спрашивает Better Auth о входе;
  - нет входа — перенаправляет на `/login`;
  - вход есть — пропускает и передаёт браузеру обновлённую куку входа.
  - Без этого срок куки в браузере не сдвигался бы: серверные компоненты не умеют ставить куки, и «30 дней с последнего захода» превратились бы в «30 дней с входа».
  - Серверные действия proxy не трогает: они проверяют вход сами и при его отсутствии отправляют на `/login`.
- Страница входа: если пользователь уже вошёл — на главную.
- Шапка (`src/app/layout.tsx`, компонент `UserMenu`): почта и кнопка «Выйти». Кнопка — форма с серверным действием `signOut`: оно удаляет вход этого устройства через Better Auth, стирает куку и открывает `/login`. Без входа шапка показывает только логотип.

Отвергнуто:

- только проверка наличия куки в proxy — дешевле, но не продлевает вход;
- только проверка в страницах — то же.

### 7. Доступ к данным — только свои

- Каждая функция в `src/lib/contacts.ts` и `src/lib/groups.ts` получает `userId` первым параметром. TypeScript не даст его забыть. Запросы фильтруют:
  - `contacts.user_id = userId`, `groups.user_id = userId`;
  - заметки — через свой контакт;
  - связи — через свои контакт и группу;
  - счётчики, фильтр по группам и «Пора связаться» — через те же условия.
- Действия с номером записи (изменить, удалить, заметка, «Связался», группа в карточке, переименовать, удалить группу) ищут запись по паре «номер + владелец». Чужая запись выглядит как несуществующая: тот же ответ «Этот контакт больше не существует.» / «Эта группа больше не существует.».
- Данные из браузера о владельце не принимаются:
  - создание и восстановление после «Отменить» ставят `user_id` текущего пользователя;
  - группы из формы и из снимка отбрасываются, если они не его;
  - контакты из снимка удалённой группы — тоже;
  - восстановление с номером, который уже занят чужой записью, ничего не делает.
- Карточка: чужой или несуществующий контакт — `notFound()`, заголовок «Контакт не найден».
- Фильтр из адреса: чужие группы отбрасываются, как удалённые.
- Создание группы: дубль названия — только среди своих групп (новый индекс).

### 8. Страницы входа и пустой список

- `src/app/login/page.tsx` с формой: клиентский компонент на `useActionState`, как остальные формы.
- `src/app/login/expired/page.tsx`: «Ссылка устарела, запросите новую» и кнопка-ссылка «Получить новую ссылку».
- Пустой список в `src/components/contacts/contact-browser.tsx`: блок «Здесь пока никого нет» получает подсказку «Добавьте первого человека, о ком не хочется забыть.» и кнопку «Добавить контакт». Кнопка открывает тот же диалог «Новый контакт», с теми же группами пользователя: второй формы нет.
- Кнопка наверху (`src/app/page.tsx`) показывается, только если у пользователя есть хотя бы один контакт. Это то же общее число контактов, что у счётчика: поиск и фильтр на него не влияют. Добавили первый контакт или удалили последний — страница обновляется после действия, как сейчас, и кнопка появляется или пропадает.
- Всё — по макетам, только дизайн-токены и компоненты shadcn/ui, которые уже есть (`Button`, `Input`, `Field`, `Card`).

### 9. Демо-данные

`scripts/seed.ts`:

- читает `OWNER_EMAIL` (пусто — понятная ошибка);
- находит или создаёт этого пользователя;
- если у него уже есть контакты — пишет «seeding skipped» и выходит;
- иначе создаёт 1 000 контактов с заметками у него и раскладывает часть по его группам с готовыми названиями.
- Чужие данные не трогает.
- На сервере seed-контейнер получает `OWNER_EMAIL` из `.env` через `deploy/compose.yaml`.

### 10. Автотесты

Vitest:

- `tests/support/auth.ts`:
  - отдельный, только тестовый экземпляр Better Auth с теми же настройками и плагином `testUtils`;
  - `signInAs(email)` создаёт пользователя и настоящий вход в тестовой базе, получает куку этого входа и кладёт её в подменённый `next/headers`.
  - Код приложения проверяет вход как обычно, через свой экземпляр Better Auth: база и секрет те же.
  - Если в установленной версии `testUtils` нет, тот же помощник проходит настоящий путь: запрос ссылки → письмо из Mailpit → открытие ссылки через обработчик Better Auth.
- Подменяются только `next/headers` и `next/cache`: без них код не работает вне Next.js.
- Письма уходят в настоящий Mailpit. Помощник `tests/support/mailpit.ts` ищет письма по адресу получателя через API Mailpit.
- У тестов свой домен почт (`@vitest.example.com`), у e2e — свой. Перед каждым тестом удаляются только письма своего домена: Vitest и e2e можно запускать одновременно.
- `cleanDb` очищает все таблицы и больше не вставляет готовые группы.
- Помощники `addContact`, `addGroup`, `putInGroup` получают пользователя.
- Все нынешние тесты переводятся на «вошёл пользователь, работает со своими данными». Их проверки не ослабляются.
- Тест миграции:
  - отдельная база `<имя>_test_migration`;
  - применяем миграции до 0003 (временная папка с усечённым списком миграций);
  - кладём контакты, заметки, группы, связи, частоты и отметки «Связался»;
  - применяем все миграции с почтой и без неё.
  - Проверяем: владелец создан, у всех записей он, число записей не изменилось. Без почты — понятная ошибка, и база осталась на 0003 с теми же данными.
- Подготовка тестовых баз передаёт в `applyMigrations` тестовую почту владельца.

Playwright:

- `e2e/support/mailpit.ts` читает письма.
- `e2e/support/auth.ts`, `signIn(page, email)`: открывает `/login`, вводит почту, берёт из Mailpit ссылку «Войти» и открывает её. Каждый e2e входит через настоящую форму и письмо.
- Пользователей с данными e2e кладёт прямо в базу (`e2e/support/db.ts`), а входит через форму.
- Сдвиг времени — правкой сроков в базе: `sessions.expires_at` / `updated_at`, `verifications.expires_at`, `login_link_requests.created_at`. Ждать 15 минут или 30 дней не нужно.

Какой тест у какого сценария — в `tasks.md`.

### 12. Выкатка

- `deploy/compose.yaml`: общий блок приложения (`x-app`) получает `OWNER_EMAIL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `SMTP_URL`, `MAIL_FROM`, все с пометкой «обязательно» (`:?`).
  - Docker compose проверяет их при первой же команде `deploy.sh` — ещё до бэкапа и миграций.
  - Забытая строка в `.env` останавливает выкатку, прежняя версия работает.

- `/health` остаётся без входа: по нему smoke-проверка понимает, что выкатка прошла.

## Risks / Trade-offs

- [Почтовые сканеры некоторых компаний открывают ссылку раньше человека и тратят её] → Человек увидит «Ссылка устарела» и запросит новую. Gmail и Яндекс так обычно не делают. Если станет проблемой — страница «Нажмите, чтобы войти» между письмом и входом; это изменение спеки, решает владелец.
- [Хостер блокирует исходящую почту на порту 465] → До выкатки проверить с сервера `nc -vz smtp.resend.com 465`. Resend принимает и на порту 2465; тогда меняется только `SMTP_URL`.
- [Письма уходят в спам] → Домен отправителя подтверждается в Resend записями DNS (SPF, DKIM — записи, которые доказывают почтовым службам, что письмо отправлено от имени домена). Делает владелец по подсказкам Resend.
- [Бесплатный Resend — 100 писем в день] → Лимиты на почту и на адрес в интернете не дают одному человеку потратить больше 10 писем в час. Для нескольких друзей хватает.
- [Друзья за одним адресом в интернете (общий Wi-Fi) делят лимит 10 писем в час] → Для нескольких друзей хватает. Число — настройка в коде, его легко поменять.
- [Забытый фильтр по владельцу в одном запросе — утечка чужих данных] →
  - `userId` — обязательный параметр каждой функции доступа к данным;
  - на каждое действие — тест «с номером чужой записи ничего не меняется»;
  - e2e A и B по критерию успеха.
- [Better Auth поменяет формат хранения ссылок, и отмена старых ссылок перестанет работать] → Удаление прежних ссылок опирается на почту внутри записи `verifications`. Тест «Запросил новую — старая не работает» поймает изменение при обновлении Better Auth.
- [Имена настроек Better Auth в 1.7 отличаются от описанных] → Сверить с документацией установленной версии. Поведение закреплено тестами, а не именами.
- [Опечатка в `OWNER_EMAIL`] → Данные достанутся пользователю с опечаткой, войти под ним нельзя. Перед выкаткой владелец сверяет строку в `.env` на сервере. Если случилось — откат вместе с базой (ниже) или исправление почты этого пользователя одной командой SQL; её запускает владелец.
- [proxy спрашивает базу при каждом открытии страницы] → Один лёгкий запрос по индексу; для нескольких пользователей незаметно.
- [Старая версия приложения не умеет обязательный `user_id`] → Откат только вместе с базой (ниже). Всё, что добавили после выкатки, при откате пропадёт.

## Migration Plan

До merge — шаги владельца (агент подскажет точные строки и команды):

1. Завести аккаунт Resend, добавить в нём поддомен `mail.percrm.ru`, внести его записи DNS у регистратора percrm.ru, дождаться подтверждения, создать ключ только на отправку.
2. С сервера проверить, что порт 465 до `smtp.resend.com` открыт. Это может сделать агент через `ssh crm`.
3. Добавить в `/home/deploy/personal-crm/.env` на сервере строки `OWNER_EMAIL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `SMTP_URL`, `MAIL_FROM`.
4. Добавить строки в локальный `.env` (значения для компьютера — таблица в решении 5).
5. Посмотреть миграцию `0005_owner_data` в PR.

Выкатка — как обычно, merge в main:

- образ → `deploy.sh`;
- docker compose проверяет новые настройки;
- бэкап базы, назван по прежней версии;
- миграции 0004–0006 одной транзакцией;
- новая версия;
- smoke `/health`.

Что бывает при сбое:

- нет настройки — выкатка останавливается до бэкапа;
- нет почты владельца при данных — останавливается на миграциях, база не меняется;
- в обоих случаях прежняя версия работает.

После выкатки — проверить руками:

- app.percrm.ru без входа показывает страницу входа;
- вход под своей почтой — то же число контактов, что до выкатки, те же группы;
- друг входит — у него пусто.

Откат — только вручную, запускает владелец, только вместе:

1. `ssh -t crm sudo -u deploy /home/deploy/personal-crm/rollback.sh` — прошлая версия приложения. Пока не восстановлена база, она открывает данные, но добавить контакт или группу не сможет.
2. `ssh -t crm sudo -u deploy /home/deploy/personal-crm/restore.sh backups/<время>_<прошлая версия>.dump` — копия базы, снятая перед выкаткой входа. Версии совпадут, `restore.sh` не будет предупреждать.

Всё, что добавили после выкатки входа, при таком откате пропадает.
