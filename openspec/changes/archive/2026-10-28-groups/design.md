# Design

## Context

Зачем фича — в `proposal.md`, что должно получиться — в `specs/contact-groups/spec.md` и `specs/keep-in-touch/spec.md`.

Как устроено сейчас:

- Таблицы `contacts` и `notes` (`src/db/schema.ts`), миграции `drizzle/0000_init.sql` и `drizzle/0001_keep_in_touch.sql`. Миграции на сервере применяет разовый контейнер (`scripts/migrate.ts`) до старта нового образа.
- Главная (`src/app/page.tsx`) — серверная страница. Всё состояние списка — в адресе: `?q=` (поиск), `?page=`, `?size=`, `?added=` (только что добавленный контакт). Адреса собирает одна функция `contactListHref` (`src/lib/search.ts`); её вызывают поиск, переключатель страниц, выбор размера страницы, диалог добавления и сам список.
- Список (`listContactsPage`) и блок «Пора связаться» (`listOverdueContacts`) — запросы в `src/lib/contacts.ts`. Счётчик под поиском и список берут данные из одного запроса (`cache()`).
- Форма контакта общая для добавления и изменения: поля перечислены в `contactFields`, все значения — строки (`ContactFormValues`), проверка — `contactInputSchema`.
- Удаление контакта с отменой: сервер отдаёт браузеру снимок (контакт и заметки), «Отменить» в течение 10 секунд (`UNDO_DURATION_MS`) отправляет его обратно (`use-delete-contact.ts`, `contactSnapshotSchema`).
- Все действия сервера (`src/app/actions.ts`) после записи вызывают `revalidatePath("/", "layout")` — страницы пересобираются со свежими данными.
- Автотестов нет: нет ни Vitest, ни Playwright, ни команды `pnpm test`.
- В проекте уже есть `@base-ui/react` (основа компонентов shadcn/ui) — в ней есть всплывающее окно (`popover`) и флажки (`checkbox`).

## Goals / Non-Goals

**Goals:**

- Две новые таблицы, существующие `contacts` и `notes` не меняются.
- Один и тот же фильтр по группам — в общем списке, в счётчике и в блоке «Пора связаться», без расхождений.
- Отметка группы в карточке — одно нажатие, отметка видна сразу, не дожидаясь сервера.
- Старая версия приложения (после ручного отката кода) работает с новой базой без ошибок.
- Тесты на настоящей базе, которые можно запустить одной командой и которые не трогают рабочие данные разработчика.

**Non-Goals:**

- Ускорение для десятков тысяч контактов и сотен групп: контактов сотни или тысячи, групп — единицы и десятки.
- Тесты интерфейса в браузере и запуск тестов в CI (позже, отдельной доработкой).

## Decisions

### 1. Две таблицы: группы и «кто в какой группе»

- `groups`: `id` (`uuid`), `name` (`text`, обязательное), `created_at`. Уникальный индекс (указатель, по которому база не даст сохранить дубль) `groups_name_unique_idx` по `replace(lower(name), 'ё', 'е')` — так «Семья» и «семья», «Ёлки» и «Елки» считаются одним названием. Это то же приведение, что в поиске по имени (`normalizeForSearch`, `nameMatches`). Длину названия (до 50) проверяет форма.
- `contact_groups`: `contact_id` → `contacts.id`, `group_id` → `groups.id`, оба с `on delete cascade` (удалили контакт или группу — связь пропадает сама). Первичный ключ — пара (`contact_id`, `group_id`): человек не может попасть в одну группу дважды. Индекс `contact_groups_group_id_idx` по `group_id` — для фильтра и для числа людей в группе.

Почему не так:

- Список групп текстом или массивом прямо в `contacts` — переименование группы пришлось бы переписывать в каждом контакте, а счёт людей и фильтр стали бы сложнее.
- Уникальность только в коде, без индекса — две вкладки могут одновременно создать «Семью» дважды.

### 2. Миграции

- `drizzle/0002_groups.sql` (создаёт `pnpm db:generate`): `CREATE TABLE "groups"`, `CREATE TABLE "contact_groups"`, два внешних ключа, уникальный индекс по `replace(lower(name), 'ё', 'е')`, индекс по `group_id`. Существующие данные не трогает.
- `drizzle/0003_default_groups.sql` (пустую создаёт `pnpm drizzle-kit generate --custom --name default_groups`, текст пишем сами): `INSERT INTO "groups" ("name") VALUES ('Аналитики'), ('Друзья'), ('Знакомые'), ('Семья'), ('Теннис') ON CONFLICT DO NOTHING`. Ни один контакт в группы не попадает.
- Обе применяются тем же разовым контейнером при выкатке, одна за другой. Упала любая — новый образ не стартует, как и раньше.
- Откат кода (`deploy/rollback.sh`): таблицы остаются, старая версия их не видит и работает как до фичи. Ничего не теряется: при повторной выкатке группы и раскладка людей на месте. Если таблицы когда-нибудь нужно убрать совсем — только вручную и с согласия владельца: `DROP TABLE "contact_groups"; DROP TABLE "groups";` и удалить две последние записи из `drizzle.__drizzle_migrations`.

Почему готовые группы — отдельной миграцией, а не в коде при старте: миграция выполняется один раз; удалённые пользователем готовые группы не вернутся сами после следующей выкатки.

### 3. Где живёт логика

- Новый `src/lib/groups.ts` (только сервер): список групп по алфавиту (`ru-x-icu`, как имена контактов) с числом людей, группы одного контакта, создать, переименовать, удалить со снимком, вернуть из снимка, поменять одну отметку контакта.
- `src/app/actions.ts`: тонкие действия сервера — проверка входных данных, вызов `groups.ts`, `revalidatePath("/", "layout")`, понятная ошибка. Нарушение уникального индекса (код Postgres `23505`) превращается в «Такая группа уже есть». В журнал — только `describeError`, как сейчас.
- Названия проверяет `groupNameSchema` в `src/lib/validation.ts`: обрезать пробелы, «Укажите название», «Название слишком длинное — до 50 символов».

### 4. Фильтр — в адресе страницы

- Параметр `groups`: `?groups=<id>,<id>` — выбранные группы, `?groups=none` — «Без группы», нет параметра — «Все». Добавляется в `contactListHref` и читается на главной рядом с `q`, `page`, `size`. Все места, где сейчас собирается адрес списка (поиск, страницы, размер страницы), передают фильтр дальше; смена фильтра сбрасывает страницу на первую.
- Сервер разбирает параметр так: берёт только правильные `id` групп, которые есть в базе; если не осталось ни одной — «Все». Поэтому ссылка с удалённой группой не ломает главную.
- Логика нажатий («Без группы» снимает группы и наоборот, повторное нажатие снимает группу, «Все» снимает всё) — отдельная функция без базы и интерфейса в `src/lib/group-filter.ts`, её легко проверить тестом.
- Почему адрес, а не память браузера: так уже устроены поиск и страницы; обновление, «назад» и ссылка в другом браузере работают сами.
- Возврат из карточки уже идёт через историю браузера (`return-to-list.ts`), поэтому фильтр сохранится без отдельного кода; если окажется, что нет, — чиним в задаче про фильтр.
- Метки групп — обычные ссылки на главную, адрес собирает тот же `contactListHref`:
  - в карточке — `contactListHref({ groups: [id] })`: только эта группа, без поиска;
  - в строке списка — текущий выбор плюс эта группа, тот же поиск и размер страницы, первая страница; если группа уже выбрана — адрес тот же. Расчёт — в `src/lib/group-filter.ts` рядом с логикой нажатий.
  - В строке списка метка стоит вне ссылки на карточку (как кнопка удаления), поэтому нажатие на неё карточку не открывает.
- После добавления контакта (`?added=`) главная, как сейчас, открывает полный список без поиска — и без фильтра. Список сам заменяет адрес на `contactListHref({ page, size })`, фильтр в него не попадает.

### 5. Запросы с фильтром

- Одно условие фильтра на `contacts.id` — общий кусок для `listContactsPage` и `listOverdueContacts`:
  - выбраны группы — для каждой `exists (select 1 from contact_groups where contact_id = contacts.id and group_id = …)`; несколько групп — все условия через `and` («во всех сразу»);
  - «Без группы» — `not exists (select 1 from contact_groups where contact_id = contacts.id)`.
- Счётчик: `total` — по-прежнему все контакты, `matched` — подходящие под поиск и фильтр. «Найдено: N из M» показывается, когда есть запрос или фильтр.
- Метки в строке: после выборки страницы — второй запрос «названия групп для этих `id` контактов» по алфавиту; `ContactListItem` получает поле `groups` — список пар `{ id, name }` (номер нужен, чтобы метка вела на фильтр).
- Пустой результат при фильтре — своё сообщение в `contact-browser.tsx` («По выбранным группам никого нет» и подсказка снять часть групп); сообщение «Никого не нашли по запросу» остаётся для поиска без фильтра.

### 6. Группы в форме контакта

- В форме — ряд флажков в виде меток (как кнопки фильтра): каждая — настоящий `<input type="checkbox" name="groupIds" value="<id>">`. Форма по-прежнему отправляется обычным образом, без отдельного кода в браузере. Список групп форма получает от сервера (главная и карточка передают его в диалоги).
- `ContactFormValues` получает `groupIds: string[]` отдельно от строковых полей — после ошибки в форме отметки остаются.
- Сохранение: `createContact` и `updateContact` в одной транзакции (несколько изменений, которые записываются в базу целиком или не записываются вовсе) пишут контакт и его группы. Группы, удалённые за время, пока форма была открыта, молча пропускаются.
- Почему не выпадающий список с несколькими значениями: групп мало, метки видны сразу и одним нажатием, на телефоне их проще нажимать. Окончательный вид — в макетах.

### 7. Быстрая смена групп в карточке

- В строке «Группы» карточки названия групп — метки-ссылки на главную с фильтром (см. решение 4).
- Рядом — кнопка, открывающая всплывающее окно (`popover` из shadcn/ui на уже установленной `@base-ui/react`) со списком групп и флажками.
- Каждое нажатие сразу вызывает действие `setContactGroup(contactId, groupId, member)` — добавить или убрать одну связь. Отметка меняется сразу (`useOptimistic`); при ошибке возвращается назад и внизу появляется сообщение.
- Почему по одной связи, а не весь список: два быстрых нажатия подряд не перетрут друг друга.

### 8. Удаление группы с отменой

- Как у контакта: `deleteGroup(groupId)` в транзакции запоминает группу (`id`, название, дата) и `id` её людей, удаляет группу (связи уходят сами) и отдаёт снимок браузеру. Вопрос перед удалением — по образцу `confirm-delete-dialog.tsx`, сообщение с «Отменить» на 10 секунд — по образцу `use-delete-contact.ts`.
- `restoreGroup(snapshot)` вставляет группу с тем же `id` (повторное нажатие ничего не ломает) и связи только с теми контактами, которые ещё есть.
- Снимок удалённого контакта (`contactSnapshotSchema`) получает `groupIds` (нет в старом снимке — пустой список); `restoreContact` возвращает связи только с группами, которые ещё есть.

### 9. Страница «Группы»

- `src/app/groups/page.tsx` — серверная страница: заголовок «Группы», кнопка «Создать группу», список групп с числом людей («0 человек», «1 человек», «2 человека» — через `pluralize`), у каждой — «Переименовать» и «Удалить». Создание и переименование — диалог с одним полем, по образцу `add-contact-dialog.tsx`.
- Ссылка «Группы» — на главной рядом с заголовком; обратно — ссылка к контактам, как в карточке.

### 10. Тестовые данные

- `scripts/seed.ts` после вставки контактов берёт пять готовых групп по названию (какие есть) и кладёт примерно две трети людей в одну-две случайные группы; остальные — без групп. Если групп нет — пропускает этот шаг.

### 11. Автотесты: Vitest на настоящей базе

- Новые библиотеки только для разработки: `vitest` (версию берём последнюю стабильную на момент установки). В образ приложения не попадает.
- Команда `pnpm test`. Перед тестами общая подготовка (`vitest` `globalSetup`) читает `.env` как остальные скрипты, создаёт в том же локальном контейнере Postgres отдельную базу `<POSTGRES_DB>_test` (если её нет) и применяет к ней все миграции. Рабочая локальная база не трогается.
- Перед каждым тестом таблицы очищаются, а пять готовых групп вставляются заново тем же текстом `drizzle/0003_default_groups.sql` — так тест «Группы после выкатки» проверяет настоящую миграцию.
- Тесты идут по одному файлу за раз (общая база).
- Тесты вызывают действия сервера и функции из `src/lib` напрямую. Подменяются только две вещи фреймворка, без которых код не запускается вне Next.js: `revalidatePath` (`next/cache`) — пустышка, и пакет `server-only` — пустой модуль. База — настоящая.
- Каждый сценарий спеки — свой тест с тем же названием. Сценарии, которые видно только глазами (вёрстка на телефоне, место фильтра на странице, вопрос перед удалением, 10 секунд на «Отменить», «назад» из карточки), сейчас проверяются руками; в `tasks.md` они перечислены отдельно и ждут Playwright.
- Старый сценарий «Поиск прячет блок» из `keep-in-touch` по решению владельца остаётся без автотеста — только руками.
- Нужен запущенный контейнер базы (`docker compose up -d`), как и для `pnpm dev`.

### 12. Макеты до кода

- Первый шаг реализации — макеты на холсте, как для «Пора связаться»: главная с фильтром, метками и блоком «Пора связаться», карточка со строкой «Группы» и всплывающим списком, форма контакта с полем «Группы», страница «Группы» с диалогами создания, переименования и вопросом об удалении. Компьютер и телефон. Копия — в `mockups/` рядом с этим файлом.
- Порядок на главной решён владельцем: заголовок → фильтр по группам → блок «Пора связаться» → поиск со счётчиком → список. Как выглядят метки (и что они нажимаются) и как фильтр помещается на телефоне — решается в макетах. Дальше — только после одобрения владельца.

## Risks / Trade-offs

- [Длинный адрес: `id` групп длинные] → Групп в фильтре выбирают одну-три; адрес никто не набирает руками. Короткие номера групп ради адреса не заводим.
- [Пока группа была удалена, создали новую с тем же названием — «Отменить» упрётся в уникальный индекс] → `restoreGroup` отвечает «Не удалось вернуть группу: группа «…» уже есть», группа не возвращается, остальное не ломается.
- [Отметки в карточке меняются сразу, а сервер может ответить ошибкой] → Отметка возвращается назад и появляется сообщение, как у кнопки «Связался».
- [Тесты зависят от запущенного контейнера и `.env`] → `pnpm test` сразу пишет понятную ошибку, если базы нет; в README — строка про `docker compose up -d`.
- [Подмена `next/cache` в тестах не проверяет, что страница обновилась] → Обновление страниц проверяется руками по сценариям; в браузерных тестах Playwright (позже) — без подмен.
- [Часть сценариев пока без автотеста] → Перечислены в `tasks.md`, проверяются руками до появления Playwright.

## Migration Plan

1. Merge в main → CI собирает образ → на сервере разовый контейнер применяет `0002_groups` и `0003_default_groups` → стартует новый образ → проверка `/health`.
2. После выкатки: на https://app.percrm.ru открыть «Группы» — пять готовых групп, у каждой «0 человек»; у старых контактов в карточке «Группы: не указано».
3. Откат — только вручную владельцем (`deploy/rollback.sh`): старая версия работает, таблицы групп остаются нетронутыми.
