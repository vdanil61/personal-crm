# Design

## Context

Мотивация и границы фичи — в `proposal.md`, поведение и критерии приёмки — в `specs/birthdays/spec.md`.

В текущем приложении контакт хранится в `contacts` (`src/db/schema.ts`). Общая форма `contact-form.tsx` обслуживает создание и изменение; серверные действия в `src/app/actions.ts` используют общую проверку из `src/lib/validation.ts`. Карточка `/contacts/[id]` получает контакт только с проверкой владельца. Удаление возвращает снимок записи для кнопки «Отменить»; перечень полей снимка задан явно и требует расширения.

На главной уже есть фильтр групп и блок `KeepInTouch`, скрываемый при непустом `query.trim()`. `resolveGroupFilter` проверяет группы пользователя, `groupFilterCondition` реализует пересечение и «Без группы». Это готовые точки подключения нового блока. Общий список выбирает только свою страницу; брать именинников из него нельзя.

Vitest запускает серверный код с отдельной настоящей базой, Playwright проверяет собранное приложение и отдельную базу в Docker. Существующие помощники `tests/support/factories.ts` и `e2e/support/db.ts` позволяют задавать поля контактов. Миграции уже выполняются до старта новой версии.

## Goals / Non-Goals

**Goals:**

- Одинаковый результат календарного расчёта независимо от часового пояса сервера и браузера.
- Пустая дата, дата без года и полная дата без выдуманного года в сохранённых данных.
- Повторное использование текущих правил владельца, фильтра, серверной проверки и обновления страниц.
- Добавочная миграция (новые поля без переписывания прежних), совместимая с откатом приложения.

**Non-Goals:**

- Новая библиотека календаря, фоновая задача, настройка часового пояса или общий рефакторинг остальных дат.
- Перенос выбора контактов в браузер или изменение существующего блока `KeepInTouch`.
- Автоматическое обновление уже открытой страницы в полночь: новый расчёт выполняется при открытии или обновлении главной.

## Decisions

### 1. Хранить три необязательных числовых поля

В `contacts` добавить `birthday_day`, `birthday_month`, `birthday_year` типа `integer`, в TypeScript — `birthdayDay`, `birthdayMonth`, `birthdayYear`.

| Состояние | `birthday_day` | `birthday_month` | `birthday_year` |
| --- | --- | --- | --- |
| Дата не указана | `NULL` | `NULL` | `NULL` |
| Известны день и месяц | 15 | 11 | `NULL` |
| Известна полная дата | 15 | 11 | 1990 |

Ограничение `CHECK` в базе разрешает только полностью пустую дату или действительные день и месяц с необязательным годом. День и месяц должны быть заполнены вместе; год без них запрещён. Год при наличии — целое число от 1 до 9999, чтобы представление и календарная проверка имели явный технический диапазон; дополнительных ограничений по возрасту не вводить. Без года допустимость дня проверяется на високосном 2000 году, поэтому 29 февраля разрешено. С годом проверяется именно указанный год. Реализовать проверку через безопасные ветви `CASE`: недопустимые части не должны доходить до вызова построения даты и вызывать исключение вместо нарушения ограничения.

Варианты: один `date` заставил бы придумывать год; текстовая дата усложняет проверку и допускает разные форматы. Три числа прямо отражают согласованные состояния и не содержат часового пояса. Пустые значения не заменяются нулями.

### 2. Один календарный расчёт для выборки и подписи

В новом `src/lib/birthdays.ts` сделать небольшие чистые функции (результат зависит только от аргументов): проверка частей даты, получение московской даты из момента `now`, определение попадания в семь дней и форматирование подписи. В рабочем запросе `now` берётся один раз на сервере; в тестах передаётся явно. Не добавлять настройку даты или тестовый переключатель в приложение.

Алгоритм:

1. Через встроенный `Intl.DateTimeFormat` с `timeZone: "Europe/Moscow"` получить год, месяц и день для одного момента `now`.
2. Построить семь календарных дат с отступами 0–6. Для прибавления дней использовать UTC как нейтральный способ работы с календарными частями, без зависимости от местного времени процесса. Для лет 1–99 избегать конструктора, который автоматически добавляет 1900.
3. Для каждого кандидата сопоставить месяц и день с каждой датой периода. Только для 29 февраля в невисокосном году сопоставлять 28 февраля. Год рождения в ежегодном сопоставлении не участвует.
4. Вернуть дату поздравления и отступ в днях; если совпадения нет, исключить контакт. Отсортировать по отступу.

Это обрабатывает смену месяца и года без сравнения строк «месяц-день». Альтернатива — сложный SQL с повторением календарных правил в нескольких местах. Для личной CRM проще один проверяемый расчёт в приложении; обращения к базе всё равно остаются только на сервере.

### 3. Отдельная серверная выборка с существующим фильтром

Добавить в `src/lib/contacts.ts` функцию `listUpcomingBirthdays(userId, filter, now)` с обязательным `userId`. База возвращает только `id`, `name`, день и месяц своих контактов с датой, удовлетворяющих `groupFilterCondition(filter)`. До расчёта упорядочить кандидатов по существующему `RU_COLLATION` и `id`; стабильная сортировка по отступу сохранит этот порядок при одинаковом дне.

Не применять пагинацию общего списка и не загружать заметки, почту и другие ненужные поля. Календарный расчёт выполняется над отобранными сервером кандидатами. Отдельный индекс по дню и месяцу пока не нужен: используется существующий индекс владельца, а объём — личная адресная книга. Ограничение по первым пяти контактам не переносить из `KeepInTouch`: согласован показ контактов за весь период.

В `src/app/page.tsx` добавить независимый серверный блок в `Suspense` под фильтром групп и перед `KeepInTouch`. Использовать существующие `readListParams`, `requireUser` и `resolveGroupFilter`. При `query.trim()` или пустой выборке возвращать `null`. Загружать данные во время запроса, как остальные данные главной, без кеширования состава между календарными днями и пользователями.

### 4. Ввод и отображение через текущие компоненты

В общей форме добавить группу «Дата рождения»: числовые поля дня и года и выбор месяца с русскими названиями. Использовать существующие `Input`, `Select`, `Field`/`FieldSet`, подписи, ошибки и дизайн-токены. Год подписать как необязательный. Специальный календарь не нужен: он предполагает полный год и потребовал бы лишних компонентов.

В форме значения остаются строками, в `contactInputSchema` проверяются и превращаются в числа или `null`. Расширить `contactFields`, типы формы, пустые значения, начальные значения в карточке и обработку ошибок. Структурную проверку календаря использовать также в `contactSnapshotSchema`, но без преобразования уже сохранённых чисел в строки. У снимков предыдущей версии отсутствующие поля считать `null`.

Добавить дату в явный список снимка `deleteContact`; восстановление через `restoreContact` должно вернуть все части. Существующие `userId` и `revalidatePath("/", "layout")` продолжают обеспечивать принадлежность и обновление главной после сохранения или возврата контакта.

В карточке добавить обычную строку `InfoItem` «Дата рождения» с годом только при его наличии. В новом `src/components/contacts/upcoming-birthdays.tsx` использовать отдельную область с заголовком «Скоро день рождения» и ссылками в карточки; имя и дата должны читаться на телефоне и с клавиатуры. Заимствовать текущие стили строк, аватар и механизм `markOpenedFromList` для возврата из карточки. Дополнительные действия и сворачивание не добавлять.

Принятые мелкие детали отображения: при совпадении дат — существующий алфавитный порядок; дата в блоке — дата поздравления текущего наступления без года, например «28 февраля» в 2027 году. В карточке остаётся исходная «29 февраля». Возраст и относительные подписи не добавляются.

### 5. Отдельный тест на каждый сценарий

В именах тестов сохранить идентификаторы B01–B30, чтобы связать их со спецификацией. Если сценарий содержит варианты, использовать отдельные параметризованные случаи для каждого варианта.

| Проверки | Основное место | Что доказывают |
| --- | --- | --- |
| B01–B05 | `e2e/birthdays.spec.ts` | Ввод, повторное открытие, изменение, очистка и результат в карточке и блоке |
| B06–B09 | `e2e/birthdays.spec.ts`, дополнительно `tests/birthday-validation.test.ts` | Ошибки в форме и независимая серверная проверка, включая прямой вызов действий с недопустимыми значениями |
| B10 | `tests/upcoming-birthdays.test.ts` и браузерная проверка границ | Реальная выборка из базы, даты 0, 6, 7 и вчера |
| B11–B16 | `tests/birthday-calendar.test.ts` | Фиксированные даты, Москва, полночь, конец года, 29 февраля |
| B17–B26 | `e2e/birthdays.spec.ts` | Видимый блок, порядок, ссылки, страницы, группы и поиск |
| B27–B28 | `e2e/birthdays.spec.ts`, дополнительно `tests/data-ownership.test.ts` | Разделение пользователей при чтении и записи |
| B29 | `tests/birthday-persistence.test.ts` | Запись без новых полей остаётся пустой и сохраняет прежние данные |
| B30 | `e2e/birthdays.spec.ts` | Удаление и отмена для даты с годом и без года |

Для B11–B16 тестировать тот же календарный модуль с явно заданным моментом, включая 2100 год как невисокосный и 2000 как високосный. Не подменять только часы браузера для серверных расчётов: это не меняет время сервера. Браузерные тесты создают даты относительно текущей московской даты и используют настоящую базу и вход через Mailpit, без моков. Календарные сценарии доступны для ручной проверки в указанные даты; обычные границы периода проверяются вводом дат относительно сегодняшнего дня. Полный перечень ручных шагов будет в README.

Каждый этап реализации начинается с соответствующего нового теста, его запуска и ожидаемого падения, затем кода и зелёного теста. Существующие проверки не ослаблять.

## Risks / Trade-offs

- Сдвиг даты из-за локального времени → единая московская дата и операции над календарными частями, отдельные проверки вокруг полуночи.
- Потеря даты при «Отменить» → расширить и явную выборку снимка, и его проверку; проверить оба состояния года.
- Расхождение интерфейса и серверной проверки → общий календарный модуль, сервер остаётся источником проверки даже при ручном запросе.
- Выборка всех кандидатов занимает больше памяти, чем SQL-фильтр по дате → возвращать только нужные поля и сначала применять владельца и группы; при существенном росте базы переносить отбор в SQL с сохранением тех же тестов.
- После отката старая версия не показывает новые поля. Её удаление с последующей отменой не знает о дате рождения и может восстановить контакт без неё → для проверки отката использовать чтение и обычное изменение; возврат к новой версии сохраняет даты у записей, которые не удаляли. Откат приложения не должен удалять новые столбцы.
- Длинный список именинников → показывать все подходящие строки, как запрошено; изменение количества видимых строк остаётся отдельным продуктовым решением.

## Migration Plan

1. В реализации создать одну миграцию `drizzle/*_birthdays.sql` и соответствующие метаданные Drizzle: добавить три допускающих `NULL` поля и ограничение календарной целостности. Не менять существующие столбцы, значения, связи или владельцев. На старых строках все три новых поля будут `NULL`, отдельное заполнение не нужно.
2. Проверить миграцию на локальной базе и на тест-стенде: прежние контакты, заметки и группы читаются, дни рождения пусты, новые даты сохраняются. Сами скрипты выкатки и CI не менять и автотестами не покрывать.
3. При выкатке использовать существующий процесс: образ с миграцией, её отдельный запуск до приложения, затем приложение и `/health`. Прод запускает владелец; при красном smoke сообщить о сбое, самостоятельно не откатывать.
4. Для отката владелец запускает существующий Deploy prod с галочкой «откат». Три поля и ограничение остаются в базе: старая версия их не выбирает явно при сохранении и продолжает работать, даты существующих записей сохраняются. Проверить это на изолированной копии до выкладки.
5. Обратная миграция с удалением полей не нужна для отката приложения и потеряет даты; не выполнять её. Восстановление из бэкапа при необходимости выполняет только владелец по текущей инструкции README.
